# Развёртывание

## Docker Compose

Основной локальный контур — `compose.yaml`: PostgreSQL 15 с persistent volume, Redis 7 без сохранения счётчиков (`save`/`appendonly` отключены; образ может создавать anonymous `/data` volume), одноразовый migrate и non-root app из одного образа. Приложение публикуется только на `127.0.0.1:${APP_PORT:-8187}`; PostgreSQL и Redis не публикуются на host. PostgreSQL, Redis и migrate используют только внутреннюю сеть backend. App подключён к backend и отдельной обычной bridge-сети frontend, необходимой для публикации loopback-порта. `docker compose up --build -d` сначала ждёт healthy PostgreSQL/Redis и успешную миграцию. При ошибке migrate приложение не запускается; startup приложения проверяет Redis и schema0002 без миграции.

Перед запуском заполните `.env` по примеру. `POSTGRES_PASSWORD` подставляется также в URL: используйте URL-safe пароль либо согласованное percent-encoding. Для production нужны `APP_ENV=production`, HTTPS PUBLIC_ORIGIN и отдельный review runtime/migrator прав. Учебный Compose использует одну DB-роль для bootstrap; это не готовая least-privilege production-конфигурация.

За host Nginx контейнер обычно видит peer как gateway Docker bridge. Определите точный gateway: `docker network inspect <project>_frontend`, проверьте фактический peer и задайте `FORWARDED_ALLOW_IPS=<gateway-IP>`. Для Nginx в отдельном контейнере задайте его стабильный точный IP. Не используйте `*` или диапазон адресов: bootstrap отвергает их. Default 127.0.0.1 подходит прямой локальной работе и не является доказанным адресом host Nginx внутри контейнера. При изменении Docker-сети сверяйте allowlist заново. Nginx должен перезаписывать X-Forwarded-For; клиент не выбирает свой IP для лимита.

Перезапуск: `docker compose restart app`, либо `down`/`up -d` для всего стенда. Без `down -v` данные PostgreSQL сохраняются. Redis restart восстанавливает квоты; бизнес-данные не затрагиваются. При runtime-отказе Redis чтение работает, запись закрыта 503; после `docker compose start redis` app перезапускать не требуется. Реальный Compose stop/start проверен 13.10.2026: чтение/preview=200, запись=503 с Retry-After:3, все 14 таблиц неизменны. Ответы 503 заняли 8,000–8,032 с: Docker DNS-разрешение имени остановленного Redis не ограничивается socket timeout 250 мс. Эти 250 мс относятся отдельно к connect/read, не к общему deadline HTTP. Проверка дампа с восстановлением в новую БД и сравнение всех 14 таблиц также пройдены; локальные доказательства — `08 Аудит/recovery-qa/compose-lifecycle/`.

Резервное копирование: выполните `pg_dump -Fc` внутри postgres-контейнера в файл, затем `docker cp` в закрытый каталог; проверьте `pg_restore --list`. Восстановление проверяйте в отдельной БД/контейнере того же major PostgreSQL, затем сопоставьте schema0002, counts и контрольное расписание/историю. Не восстанавливайте поверх единственного рабочего volume. Проверка TOC без restore rehearsal не считается проверкой восстановления.

Откат этого архитектурного релиза — возврат предыдущего совместимого со schema0002 приложения и окружения. `login_attempts` сохранена, схема не понижалась. После подтверждения старого приложения Redis можно остановить. Код до0002 использовать нельзя. Production-переключение требует отдельного согласования и проверенного backup.

## Альтернативный systemd-контур

Приложение работает как один Python-сервис. Он отдаёт API и собранный React-клиент; Nginx завершает TLS и проксирует запросы. PostgreSQL и Uvicorn слушают только loopback.

Шаблоны в этой папке рассчитаны на отдельный домен `schedule.example.org`. Перед установкой замените домен, пути сертификатов и каталоги. Не заменяйте ими конфигурацию действующего сервера целиком.

## Подготовка

1. Создайте системного пользователя `schedule`, каталог `/opt/schedule/releases` и БД `schedule`.
2. Установите расширение `btree_gist`. Для миграций используйте отдельную роль-владельца `schedule_migrator`; для приложения — `schedule_app` без SUPERUSER и DDL-прав.
3. Подготовьте отдельный Redis, доступный только приложению; проверьте PING. Разместите исходники в новом каталоге релиза. Создайте venv и установите `requirements.lock`.
4. В `frontend` выполните `npm ci` и `npm run build`. Node.js нужен для сборки, не для работы сервера.
5. Примените `alembic upgrade head` с миграционным подключением. Выдайте runtime-права по [grant-runtime.sql](grant-runtime.sql).
6. Создайте ссылку `/opt/schedule/current` на подготовленный релиз.

Не переносите на сервер локальные `.env`, `.local`, зависимости или тестовую базу. Утилита `app.seed` предназначена для локальных проверок старой схемы и запрещена в production.

## Окружение

Файл `/etc/schedule/schedule.env`: владелец root, группа schedule, права 0640.

```dotenv
APP_ENV=production
DATABASE_URL=postgresql+psycopg://schedule_app:CHANGE_ME@127.0.0.1:5432/schedule
PUBLIC_ORIGIN=https://schedule.example.org
APP_BASE_PATH=/
GUEST_MODE=1
REDIS_URL=redis://127.0.0.1:6391/0
REDIS_CONNECT_TIMEOUT_MS=250
REDIS_READ_TIMEOUT_MS=250
FORWARDED_ALLOW_IPS=127.0.0.1
```

В согласованном systemd-контуре выделенный Redis планируется на числовом loopback `127.0.0.1:6391`; порт должен соответствовать фактической конфигурации Redis. Такой адрес исключает DNS-задержку подключения. Не закрепляйте в REDIS_URL случайный IP контейнера: он может измениться при recreate. Локальная Compose-проверка не является доказательством установки Redis или переключения production.

`CHANGE_ME` — заглушка. Пароль с особыми символами необходимо URL-кодировать. Не храните заполненный файл в Git.

При размещении в подпапке согласуйте три настройки:

| Настройка | Пример |
| --- | --- |
| База Vite при сборке | `VITE_BASE_PATH=/mireabackr/` |
| Путь cookie | `APP_BASE_PATH=/mireabackr` |
| Nginx | Удаляет префикс `/mireabackr/` при передаче запроса в Uvicorn |

`PUBLIC_ORIGIN` содержит только протокол и домен, без пути. Для отдельного домена оставьте Vite base и путь cookie равными `/`.

## Сервисы

- [schedule.service](schedule.service) запускает приложение от непривилегированного пользователя.
- [nginx.conf](nginx.conf) содержит пример HTTPS-прокси и ограничения частоты запросов.
- [schedule-cleanup.service](schedule-cleanup.service) и [schedule-cleanup.timer](schedule-cleanup.timer) удаляют просроченные демо раз в час.

Проверьте `nginx -t` перед перезагрузкой. Uvicorn доверяет forwarded-заголовкам только от 127.0.0.1; Nginx перезаписывает X-Forwarded-For реальным IP. Если используется CDN, отдельно настройте доверенные адреса прокси.

В production документация `/docs` отключена, cookie имеет Secure, HttpOnly и SameSite=Strict. Изменяющие запросы требуют CSRF-токен; проверяется Origin. Демо ограничено по числу записей и частоте операций.

## Обновление и откат

1. Прогоните тесты на отдельной БД и соберите клиент.
2. Сделайте `pg_dump -Fc` в закрытый каталог. Проверьте архив через `pg_restore --list`; периодически проверяйте восстановление в отдельной БД.
3. Подготовьте новый каталог релиза и примените необходимые миграции.
4. Переключите `current`, перезапустите только сервис приложения.
5. Проверьте HTTPS, `/api/v1/health`, создание личного демо, смену роли и сохранение занятия.

Откат к предыдущему коду допустим только при совместимой схеме. **Код до миграции 0002 нельзя запускать на новой базе:** он не разделяет данные по пространствам. Для такого отката требуется восстановление подходящей резервной копии в отдельную БД.

Логи не должны содержать пароли, cookies, тела запросов или полный DATABASE_URL. События приложения содержат сценарий/маршрут, статус, correlation_id и класс ошибки без SQL и параметров. Ответ 503 сопровождается Retry-After; запись автоматически не повторяется.

Сценарный прогон `scripts/smoke_guest.py <base-url>` создаёт собственные тестовые демо. На рабочем сайте запускайте его только в рамках согласованной проверки.
