# Архитектура

Сервер — модульный монолит с направлением зависимостей к внутренним слоям. Один FastAPI-процесс обслуживает API и собранный React-клиент. PostgreSQL — источник истины; Redis используется только для ограничений частоты запросов.

```text
HTTP / Pydantic / cookie / CSRF
              ↓
api → application → domain
          ↑            ↑
  PostgreSQL / Redis / crypto adapters
              ↑
          bootstrap.py
```

`domain` содержит значения и чистые правила московского дня, учебного периода, активности справочников, вместимости, разворачивания серии и канонического payload hash. `application` содержит именованные сценарии авторизации, профиля, справочников, пользователей, периодов, расписаний, занятий, серий и обслуживания. Оба слоя не импортируют FastAPI, SQLAlchemy, Redis или Pydantic. Это проверяется AST-тестом, включая заведомо запрещённый импорт как отрицательный контроль. Внутренние ошибки — смысловые Unauthorized, RateLimited(policy, retry_after_seconds), DependencyUnavailable и другие; HTTP-коды, response envelope и Retry-After определены исключительно в api/errors.py. Отдельный oracle запрещает возврат этих контрактов во внутренние слои; сценарий Login запускается в свежем Python-процессе с запретом импорта framework-пакетов.

`application/ports.py` задаёт Protocol-контракты UoW, четырёх сценарных репозиториев, MutationLimiter, PasswordHasher, TokenService и Clock. Репозитории возвращают обычные Python-значения, не ORM-объекты. Входные Pydantic-схемы преобразуются маршрутом в dataclass DTO. `bootstrap.py` выбирает реализации; `main.py` только экспортирует собранное приложение. Совместимые `models.py`, `db.py`, `security.py` переэкспортируют прежние имена для Alembic, тестов и служебных команд.

## Транзакции и изоляция

Каждый сценарий записи сначала проверяет права и атомарно получает лимит Redis, затем входит в явный PostgreSQL UoW. Лимит не компенсируется, если последующая транзакция откатилась. API-зависимость больше не делает неявный commit. Чтение не требует Redis и не берёт write-lock.

Для tenant-операций RequestContext явно содержит workspace_id, user_id, role и is_guest. Запросы репозиториев содержат workspace-предикаты, в том числе для связей, counts и истории. ORM loader/before_flush hooks остаются вторым уровнем защиты; составные внешние ключи PostgreSQL запрещают смешанные tenant-ссылки независимо от кода.

Запись в пространстве сериализуется advisory lock, ожидание — максимум две секунды. После ожидания снова проверяются активность пользователя и полномочия: параллельная смена роли не даёт уже ожидающему запросу сохранить старые права. У login и создания демо явный SystemContext: эти операции ещё не имеют аутентифицированного tenant-контекста. Создание демо дополнительно сериализует проверку общей ёмкости.

Занятие и соответствующая история находятся в одной транзакции. Перенос/отмена проверяют version; PostgreSQL exclusion constraints независимо защищают от пересечения группы, преподавателя и аудитории. Серия и все занятия сохраняются одной транзакцией. Ключ идемпотентности и SHA-256 payload хранятся в PostgreSQL; одинаковый ключ и payload возвращают прежние ids с replayed=true, другой payload — 409. Семантика истории сохранена: отдельные события created/moved/cancelled и снимки до/после; повторный publish уже опубликованного расписания не создаёт событие.

Миграции 0001/0002 не переписаны. Schema 0002, таблицы, ограничения, значения и audit history сохранены. `login_attempts` оставлена для совместимого отката; новые лимиты туда не пишутся и от её строк не зависят.

## Redis

Lua-сценарий сначала читает все счётчики и TTL запроса. Если хотя бы один достиг лимита, он возвращает отказ и максимальное время ожидания среди достигнутых лимитов, ничего не увеличивая. Иначе увеличивает каждый bucket и назначает TTL первому значению или записи без TTL. Все действия выполняются одним EVALSHA; NOSCRIPT разрешает одну загрузку скрипта и один повтор. Сетевые/скриптовые ошибки не ретраятся и закрывают запись ответом 503 + Retry-After: 3. Connect/read timeout — не более 250 мс каждый, но это не общий deadline операции: системное DNS-разрешение имени выполняется до socket timeout. При остановке Redis-контейнера в проверенном Compose запись возвращала 503 за 8,000–8,032 с; отдельно DNS занял 8,0803 с, а соединение по известному числовому IP — 0,2601 с. Для локального production Redis числовой loopback-адрес исключает эту DNS-задержку, но не превращает socket timeout в гарантированный end-to-end deadline.

| Политика | Buckets |
| --- | --- |
| Login | IP 60/900 с и нормализованный account 10/900 с |
| Новое демо | IP 10/900 с |
| Аутентифицированная запись | Workspace 120/60 с, общий для всех маршрутов |
| Сброс демо | Workspace-write и guest-create одновременно |
| Maintenance cleanup | Общий служебный bucket 120/60 с |

Ключ имеет вид `schedule:<environment>:rl:v1:<bucket>:<sha256>`. Raw IP, username, cookie и токены в ключи и события приложения не попадают. Несколько политик намеренно используют общий bucket: например, смена профиля и logout расходуют один workspace-лимит, а reset — тот же guest-лимит, что создание демо.

При runtime-сбое Redis health проверяет только доступность чтения PostgreSQL. Существующая валидная guest-сессия, GET-маршруты и POST series/preview остаются доступны. Новый guest/login, reset, профиль, logout и все изменения данных возвращают 503 до мутации. После восстановления Redis запросы работают без рестарта. При холодном старте проверяются Redis и версия схемы; миграция выполняется отдельным job, а не startup hook.

Uvicorn принимает forwarded IP только от адресов FORWARDED_ALLOW_IPS; bootstrap запрещает wildcard и сетевые диапазоны. Host Nginx перед Docker обычно виден как bridge gateway: оператор должен определить этот точный адрес. Непроверенный X-Forwarded-For от прямого клиента игнорируется. Compose публикует только loopback-порт приложения через обычную bridge-сеть frontend. App также подключён к внутренней backend-сети; PostgreSQL, Redis и migrate находятся только в backend.

## Сетевые ошибки и наблюдаемость

Клиент не повторяет автоматически неоднозначную запись. Для профиля после timeout/5xx выполняется ровно один GET auth/me с отдельным сроком ожидания; успех принимается только при совпадении id, role, name и role-specific group/teacher id. Для серии безопасный повтор использует прежний idempotency key. Остальные операции требуют повторного чтения состояния перед решением пользователя.

Приложение пишет события rate_limit_denied, redis_unavailable, db_unavailable, workspace_lock_timeout, mutation_committed и request_finished. Ответ получает X-Request-ID; события связываются correlation_id, содержат сценарий, смысловой outcome и длительность там, где она измеряется. HTTP-слой отдельно записывает маршрут и status в request_finished. Тела, cookies, credentials, raw usernames/IP и DATABASE_URL в эти события не включаются. В контейнере стандартный Uvicorn access log с адресами клиентов отключён; события schedule.events выводятся собственным stderr handler. Это журнал событий, а не настроенная система внешних метрик/алертов.

## Границы решения

Redis — одиночный экземпляр, без сохранения счётчиков (`save` и `appendonly` отключены); квоты сбрасываются при restart. Образ Redis объявляет `/data` и может создавать anonymous volume, поэтому отсутствие persistence не означает отсутствие volume. Multi-key Lua не рассчитан на Redis Cluster. Fixed window допускает всплеск на границе окна. Workspace-wide lock ограничивает throughput одного пространства, сохраняя простую проверяемую транзакционность. Изменение этих решений требует измерений и отдельных конкурентных тестов.

Compose предоставляет воспроизводимый учебный стенд. Production-switch, резервная копия и проверенное восстановление требуют отдельной процедуры и разрешения; новая архитектура сама по себе не доказывает пригодность всех настроек стенда для production.
